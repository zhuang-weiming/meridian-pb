## A. Avaloq 能力边界：强在哪、弱在哪

<!-- source: 02-functional-architecture/02-avaloq-boundary.md -->

> 依据：外部源码审计目录 `/Users/weimingzhuang/Documents/source_code/avaloq/doc`（K/AFS、package/procedure、table/column/constraint、配置基线）与 Avaloq 官方产品页。
> 重要：**本文分析 Avaloq 的能力，是为了“自研重写”的需求基线，不是保留/续订计划。** 目标是用自有系统替换 Avaloq，Avaloq 仅作能力参考与迁移来源。
> 重要：**“未找到”不等于“没有”**；本文把“源码/产品证据”与“待验证假设”分开。
> 证据等级：A 源码/表结构直接证据；B 官方产品文档；C 行业/同事口径；D 待验证。

### 0. 先修正上一版的三个错误

#### 错误 1：“Avaloq 的强项是 TAX2/报告，所以它能做个人税务申报”

**不对。**

- `TAX2_EVT#CALC` / `TAX2_EVT#` 是 **Avaloq 自己系统内的事件/交易税计算与结果记录**：按 tax type、日期、BU、object、direction、settlement plan、currency、classification 等选规则，计算/换算/记入 `TAX2_EVT_SERPIL`。
- 它处理的是 **Avaloq 账本内的交易/持仓/事件**；它不会自动知道客户在行外的工资、版税、私股、信托分配、海外实体。
- EasyTax 是瑞士各州税务申报生态的集成/产品，不是全球个人税务申报引擎。
- CRS/FATCA 是账户分类/报告，不是个人报税表。

**正确说法：**

> Avaloq 是“银行侧交易税/预扣/报告引擎”；不是“全球个人综合所得税申报平台”。

#### 错误 2：“Avaloq 没有工作流/客户生命周期”

**不对。**

- 源码审计：22,455 个存储过程；**58.4%** 是 `TASK_*`/`TQ_*`/`WFC_*` 工作流/任务；**26.7%** 是 `NETW_*` 集成；**14.9%** 是核心业务。
- 有 `DOC` 通用单据、`WFC_STATUS/ACTION/RULE`、`DOC_CLT` 客户生命周期、`TASK_DOC_CLT` 工作台。
- 所以它有“单据/任务/客户生命周期”，但**不是“法律事件/授权/证据”的生命周期**。

#### 错误 3：“Avaloq 没有税务/抵押/信贷能力”

**不对。**

- `TAX2` 有真实的税事件/规则/金额/反向/持久化。
- `COLLAT_LOT_DISTR#CMPL`、`LIHI`、`CRED_CRIT_DSP#AGGR_PROC`、`HS$CREDIT_PD_PROC` 等有抵押/额度/信用风险。
- 它缺的是 **私股估值治理/IPO 生命周期/跨境质押执行/义务日历**，不是“折价率/抵押金额”这类基础字段。

- **不在范围**：银行本来就不该做，或应合作。

### 3. TAX2 深读：它到底做什么

#### 3.1 调用链

```
TAX2_EVT#CALC
  → TAX2_EVT#.VAL
    → TAX2_EVT_RULE#.GET_RULE   (选规则)
    → TAX2_EVT_VAL#.TAX2_EVT#VAL (算金额)
    → TAX2_EVT_SERPIL#.ADD_REC   (结果)
  → TAX2_EVT#REVS                (反向)
  → TAX2_EVT_SERPIL#.PUT         (持久化)
```

#### 3.2 规则选择

- 按 `TAX_TYPE`、日期、BU、object、direction、settlement plan、currency、classification 等过滤。
- 候选按 `SEQ_NR, PRIO DESC`；同一 sequence 第一个通过 post-query checks 的候选被接受。
- `COND` 是动态 SQL/表达式；返回 `+` 才通过。
- 汇率按事件/ posting sequence/ cost key 的最近 sequence 选；不是“执行时间最近”。

#### 3.3 金额

- 方法 1：`VALUE_AC = TO_NUMBER(VALUE1) * AMOUNT / 100`（百分比）。
- 方法 2：汇率方法。
- 其他：复用事件金额/方法。
- `VALUE_TC = MP_CURRY.RD(DEST_SGN * VALUE_AC * XRATE, TaxCurrency, TRUE)`（简化）。
- NULL 不会被自动当 0；缺百分比可能产生 NULL，不是“零税”。

#### 3.4 它不做什么

| 不做 | 说明 |
|---|---|
| 不看行外收入 | 只处理 Avaloq 内的事件/持仓 |
| 不判断税务居民身份 | 身份是输入/分类，不是 TAX2 自动判定 |
| 不做个人综合所得税申报 | 无 UK/HK 个人报税表 |
| 不做税务建议 | 规则/配置，不是法律意见 |
| 不做跨境协定筹划 | 可配置预扣/协定，但不是顾问 |
| 不做 CRS/FATCA 个人申报 | 报告是账户分类/交换，不是个人税表 |

#### 3.5 正确使用

- 银行侧：交易税/预扣/税务事件/报告。
- 客户侧：tax data pack（来自自研核心/迁移数据 + 行外 + 实体 + 顾问）。
- 责任：银行对数据/预扣/报告负责；客户/顾问对申报/结论负责。

### 4. 其他能力的真实边界

#### 4.1 客户/关系

- `OBJ_BP`/`OBJ_PERSON`/`OBJ_CONT`/`OBJ_PERSON_REL2`/`OBJ_BP_PERS_REL_AUTH` 能记录人/公司/合同/关系/代表/参与/授权字段。
- 但源码审计明确：
  - 没有通用 25% UBO 阈值；
  - 没有自动最终自然人穿透；
  - 没有家庭继承签字权；
  - `AUTH_ROLE`/`LIMIT`/`SIGN_LIST` 是记录，不是完整授权算法。
- 所以：Avaloq 可作为“人员/关系/授权字段”的输入，不是“法律授权图谱”的事实源。

#### 4.2 文档/工作流

- `DOC` 有 `META_TYP_ID`/`WFC_STATUS_ID`/`WFC_ACTION_ID`/dates/BP/CONT；`WFC` 有状态/动作/规则缓存；`DOC_CLT` 有客户生命周期/工作项/FDM。
- 但它是“单据/任务”模型，不是“法律事件/授权/证据”模型；没有 `Authority`/`EstateCase`/`ProbateCase`/`EvidencePack` 的原生语义（待验证）。
- 可作为文档/任务/审批的执行端；新核心做法律/证据/编排。

#### 4.3 信贷/抵押

- `COLLAT_LOT_DISTR#CMPL` 编译累计百分比/分段；`LIHI` 额度层级；`CRED_CRIT_DSP`/`HS$CREDIT_PD_PROC` 信用风险。
- 但源码审计：抵押分段/额度节点不等于“已批准授信”；估值/折扣/LTV/执行仍需信贷/估值委员会。
- 所以：Avaloq 做“额度/抵押/风险”的记录与计算；新核心做“私股估值治理/质押执行/生命周期”。

#### 4.4 私股/Pre-IPO

- Avaloq 的信贷/抵押能记录抵押品/额度/追保；但没有 `PrivateAsset` 生命周期、融资轮、lock-up、IPO 窗口、secondary、forward、义务日历（待验证）。
- 所以：Avaloq 做“账/额度”；新核心做“生命周期/治理/证据”。

#### 4.5 税务/合规

- TAX2/CRS/FATCA/报告强；个人税包/行外/多实体/私股弱。
- 制裁/PEP/AML 有监测/审计线索；但高风险判断/来源/目的/上报仍是人+规则+证据。

### 5. 替换 vs 扩展：三种方案

| 方案 | 范围 | 优点 | 缺点 | 适用 |
|---|---|---|---|---|
| **A. 扩展 Avaloq** | 在 Avaloq 上加家族/授权/案件/私股对象/工作流 | 迁移低；复用账本/信贷/支付 | shadow core；双份数据；升级更贵；每加一条旅程多一层定制 | T5 未证明；短期 |
| **B. 分阶段自研替换** | 自研 L1/L2；自研 L0 按产品/辖区替换；Avaloq 仅参考/迁移 | 语义正确；渐进；可回退；业务见效快 | 双跑/集成/数据 ownership/组织；需要明确不续订时间表 | **推荐（目标：不续订 Avaloq）** |
| **C. 全量替换** | L0–L2 全换 | 单平台；长期简单 | 迁移 544 表/1,298 适配器/并行/监管/供应商退出；最高风险 | T5 明确证明 |

#### 5.1 为什么推荐 B

1. **Avaloq 的强项是 L0**：交易/账本/支付/信贷/税务事件；把它作为能力参考和迁移来源，而不是长期平台；风险通过分阶段自研/双跑管理，目标是不续订。
2. **新核心的差异化是 L1/L2**：家族/授权/事件/证据/私股生命周期；这些 Avaloq 不擅长。
3. **HSBC 定制层巨大**：544 表/335 存储过程/155 函数/1,298 适配器；全量替换的迁移/并行/监管成本极高。
4. **分阶段**：先建 L1/L2，用 D1/D3/D2 证明价值；12–18 个月后开始 L0 迁移，而不是决定“是否保留”。
5. **供应商路线**：Avaloq 在云/API/PE/信贷上持续投入；替换必须跑赢 roadmap，而不只是“功能更多”。

#### 5.2 什么时候才考虑 C

- T5 量化证明：扩展的 3 年 TCO/变更速度/升级风险明显劣于替换；
- 供应商退出/合同/监管压力；
- 有可参考的同类私行全量迁移成功案例；
- 有 36–60 个月的预算/组织/并行能力；
- 监管/客户/董事会接受迁移风险。

> 没有这五个条件，宣布“全量替换 Avaloq”是不负责任的。

### 6. 给供应商/架构团队的 12 个问题

1. `OBJ_BP_PERS_REL_AUTH` 能否表达“文书类型/范围/生效/失效/辖区/登记”？还是只是字段？

4. 是否有 `EvidencePack`/`DecisionRecord`/法院级审计？还是日志？
5. 私股/Pre-IPO 是否有 `PrivateAsset`/`ValuationGovernance`/`Pledge`/`Obligation`/`Exit`？
6. TAX2 能否接收行外收入/实体/信托分配？还是只处理 Avaloq 事件？
7. CRS/FATCA 报告能否生成“客户税包”，还是只有监管 XML？
8. 多实体/多辖区/多币种/多语言/多时区如何支持？
9. API/事件/Webhook 的覆盖/延迟/幂等/权限？
10. 升级/定制/云/退出条款？HSBC 定制层如何迁移？
11. 数据模型是否支持 consent/目的/角色/字段级权限？

## B. 替换商业论证：先讲生意，再讲技术

<!-- source: 02-functional-architecture/05-avaloq-replacement-business-case.md -->

> 结论：**Avaloq 是要被替换的，不是长期保留的“账本”；也不是继续订阅。**
> 目标状态是 **自研家族核心 + 自研交易/账本平台**；以 Avaloq 作为能力参考和数据迁移来源，重写为自有系统，最终不续订 Avaloq。
> 本文先给业务论证；如果业务数字仍不被接受，再给 IT 设计/自主研发/降本论证。

---

### 0. 一句话

> **不是“Avaloq 不好”，而是“Avaloq 的主键是账户/交易，HSBC 下一阶段的增长主键是家族/代际/跨境/证据”。**  
> 继续在 Avaloq 上叠加，会把新能力做成“影子核心”；替换，才能把客户生命周期变成可复用、可扩展、可衡量的平台。

### 1. 业务上为什么不能继续

#### 1.1 收入：新客群/新服务上不去

| 业务问题 | Avaloq 现状 | 业务代价 |
|---|---|---|
| 家族/下一代/家办需要“家族图 + 角色 + 治理 + 教育 + 家办” | 账户/合同/关系字段；不是家族生命周期 | 下一代激活慢、钱包份额低、家办被 MFO/律师拿走 |
| 跨境搬迁/多实体/多辖区 | 多实体可做，但跨实体编排靠人/邮件 | 开户慢、重复 KYC、客户体验差、流失 |
| 私股/Pre-IPO 需要估值/质押/义务/退出生命周期 | 有标准信贷/抵押；缺私股生命周期 | 失去高价值信贷/退出/信托收入 |
| 税务数据包/顾问协同 | TAX2 是账本内交易税；看不到行外收入/实体 | 客户/顾问体验差；税务服务收入让给外部 |
| 家办/CIB/Access 需要机构级产品编排 | 交易/账本强；家族/家办/生态弱 | 家办客户被 UBS/Citi/JPM 拿走 |

**业务结论**：Avaloq 能支撑“账户服务”，但支撑不了“家族关系 + 代际 + 家办 + 跨境 + 私股”的增量收入。

#### 1.2 成本：定制层越滚越大

- HSBC 定制层：**544 张表、335 个存储过程、155 个函数、1,298 个网络适配器**（`HS$`/`NETW_HS$`）。
- Avaloq 实施/升级被独立评价为“comparatively cost- and resource-intensive”；存在 customization layer；TCO 是客户核心关注。
- 每加一条新旅程（家族/授权/证据/私股），都在 Avaloq 上加一层定制 → 升级更难、测试更贵、人才更贵。
- 业务代价：**变更慢、成本高、创新预算被维护吃掉**。

#### 1.3 风险：监管/运营/供应商

- 监管：FINMA 2024（PEP/AML）、DOJ 2019（税务）、CRS/FATCA、运营韧性、数据跨境。
- 运营：手工证据/对账/跨实体；关键人依赖；升级窗口。
- 供应商：深度定制导致锁定；退出/迁移成本高；roadmap 不完全对齐 HSBC。
- 业务代价：**罚款/ remediation/客户信任/董事会关注**。

#### 1.4 速度：新服务从“想法”到“上线”太慢

- 家族办公室/下一代/私股/税务数据包，需要新对象/事件/权限/证据；Avaloq 的模型/定制/升级节奏不支持“按月迭代”。
- 竞争对手（UBS/Citi/SCB）用独立家办团队/平台/合作，速度快。
- 业务代价：**错过下一代、错过退出窗口、错过家办迁移**。

#### 1.5 客户：体验碎片化

- 同一家族在不同实体/portal/团队之间重复 KYC/文件/解释。
- 下一代没有独立体验；配偶/受益人是“附属”。
- 压力时刻（失能/身故/争议）靠人、邮件、PDF。
- 业务代价：**NPS/留存/转介下降**。

### 2. “替换”到底替换什么

#### 2.1 目标架构

```
L3 体验：RM Cockpit / Family Portal / NextGen App / FO Dashboard
L2 家族生命周期核心（新）：Family / Authority / Goals / Events / Governance / Evidence
L1 客户/法律主体/关系（新）：Party / Entity / Trust / Estate / UBO
L0 交易与账本（新）：Positions / Trades / Payments / GL / Credit / Tax
```

**目标：L0–L2 全部迁移到自研平台；Avaloq 只作为能力参考与数据迁移来源，不再续订、不再作为长期账本。**

#### 2.2 不是“换个 UI”

- 不是把 Avaloq 页面换皮；
- 不是在新核心后面永久挂一个 Avaloq；
- 不是只做“客户 360”；
- 是 **主键/事件/证据/数据模型/集成/账本** 的替换。

#### 2.3 自研重写，不是“换一个订阅”

目标不是从“订阅 Avaloq”换成“订阅另一个厂商”，而是：

- **自有代码/数据模型/路线图**：核心由 HSBC 自研团队拥有和演进；
- **Avaloq 只作参考**：参考领域模型、流程、算法边界和源码审计结论，不复用其专有代码，不做知识产权侵权式复制；
- **商品化组件可买/合作**：风险分析、聚合、税务申报、估值、信托行政等，买/合作优于自建；
- **不续订**：合同到期前完成数据迁移/对账/退出；不把 Avaloq 作为长期运行时依赖。

#### 2.4 过渡期策略

- **Phase A**：自研 L1/L2 家族核心；Avaloq 仅作需求参考/迁移数据源（如合同允许短期只读）。
- **Phase B**：自研 L0 交易/账本模块逐步替换 Avaloq（按产品/辖区/实体）。
- **Phase C**：Avaloq 不续订；数据归档；合同退出；自有平台单核运行。

### 3. 商业论证：五类价值

> 下列公式是“怎么算”的模板，不是 HSBC 实际数字。需要内部数据填入。

#### 3.1 收入增长

| 价值池 | 机制 | 指标 |
|---|---|---|
| 下一代激活 | 课程 → 独立账户 → 首投/创业/慈善 | 下一代客户数、AUM、钱包份额 |
| 家办 | 合并/投资/信贷/信托/CIB | 家办 AUA、收入、渗透 |
| 跨境 | 搬迁/多实体/多辖区 | 跨境客户数、收入、留存 |
| 私股/Pre-IPO | 估值/质押/退出/信托 | 信贷余额、交易/顾问费 |
| 税务数据包 | 顾问协同/报告/预扣 | 税务服务收入/留存 |

**公式：**

> 增量收入 = 新增家族数 × 家族年均收入 + 现有家族钱包份额提升 × AUM × 费率 + 下一代激活 × 终身价值。

#### 3.2 成本下降

| 价值池 | 机制 | 指标 |
|---|---|---|
| 去定制 | 减少 `HS$` 表/过程/适配器 | 定制对象数、升级人天 |
| 自动化 | 家族/授权/事件/证据/对账 | 人工小时、返工率 |
| 供应商整合 | 减少重复系统/合同 | 许可/运维/集成成本 |
| 云/API | 弹性/复用 | 单位交易成本、上线时间 |

**公式：**

> 成本下降 = 人工小时 × 全载成本 + 定制/升级人天 × 费率 + 许可/运维节省 + 返工/差错成本。

#### 3.3 风险下降

| 风险 | 机制 | 指标 |
|---|---|---|
| 监管罚款/ remediation | 证据/审计/CRS/FATCA/AML | 罚款、整改成本、审计发现 |
| 无权支付/越权披露 | Authority/Consent/Evidence | 事件数、赔付、投诉 |
| 运营错误 | 自动化/对账 | 差错率、返工 |
| 供应商锁定 | 开放架构/退出 | 迁移成本/议价 |

#### 3.4 资本/敏捷

- 新服务上线时间（月→周）；
- M&A/合作/新市场接入时间；
- 数据/API 复用；
- AI/分析 readiness。

#### 3.5 客户留存

- 跨代客户数；
- 下一代激活；
- 家办留存；
- NPS/转介；
- 压力时刻满意度。

#### 3.6 一个“示范性”账本（不是 HSBC 数据）

> 假设：500 个高净值事件/年；每件 20 小时；全载 $150/小时；返工 30%；外部法律/专业费 $2m/年；流失 AUM $500m × 1% 利润率；变更 20 人 × $200k/年。
>
> 现状年成本 ≈ 500×20×150 + 2m + 返工 + 5m + 4m ≈ **$12.5m+/年**（不含罚款/机会成本）。
>
> 若新核心降低 30% 人工/返工、减少 50% 变更、挽回 20% 流失，3 年价值可能 > **$15–25m**；这还不含增量收入。
>
> **这不是 HSBC 的实际数字；是用来要求内部数据的模板。**

### 4. 如果业务讲不清：IT 设计/自主研发论证

> 用户要求：业务讲不清，就用 IT 设计讲，自主研发、减少 cost。以下是备用论证。

#### 4.1 技术债务

- 544 表/335 过程/155 函数/1,298 适配器：升级/测试/人才/文档成本。
- 账户/交易主键与家族/授权/事件/证据不匹配：每加一条旅程都是“补丁”。
- 单体/批处理/定制层：云/API/AI/实时能力受限。

#### 4.2 目标 IT 架构

| 原则 | 做法 |
|---|---|
| **模块化** | 家族/授权/事件/证据/私股/税务/账本独立模块 |
| **API/事件** | 所有跨模块 via API/event；idempotent/as-of |
| **云原生** | 弹性/可观测/灾备/数据驻留 |
| **配置化** | 辖区/产品/规则/权限版本化，减少代码定制 |
| **数据平台** | 统一客户/家族/事件/证据数据；AI-ready |
| **开放生态** | 合作/买/自建组合；避免锁定 |
| **安全/合规** | 最小权限/加密/审计/Chinese Wall |

#### 4.3 自研 vs 买

| 组件 | 建议 |
|---|---|
| 家族/授权/事件/证据/治理 | **自研**（差异化） |
| 交易/账本/结算/托管 | **买/合作**（成熟平台）或自研长期替换 |
| 风险/组合分析 | 买（Aladdin） |
| 聚合/报表 | 买/合作（Addepar） |
| 税务申报/法律/估值/信托 | 合作 |
| AI 底座 | 买/合作；自研受限场景 |

> “自主研发，减少 cost”不等于“全部自研”；是 **把差异化自研、 commodity 买/合作**，降低总成本。

#### 4.4 成本对比（IT 视角）

| 项目 | 继续 Avaloq | 新平台 |
|---|---|---|
| 定制/升级 | 高（544 表/1,298 适配器） | 低（配置/API） |
| 新服务上线 | 9–18 月 | 3–6 月 |
| 云/弹性 | 受限 | 原生 |
| 数据/AI | 难 | 易 |
| 供应商锁定 | 高 | 低 |
| 迁移风险 | 低短期/高长期 | 高短期/低长期 |

### 5. 选项与建议

| 选项 | 描述 | 结论 |
|---|---|---|
| **A. 继续扩展 Avaloq** | 在 Avaloq 上加家族/授权/证据/私股 | **不推荐**：影子核心、升级更贵、长期锁定 |
| **B. 分阶段自研替换** | 自研 L1/L2；自研 L0 按产品/辖区替换；Avaloq 仅参考/迁移 | **推荐**：风险可控、可回退、业务见效快；目标不续订 |
| **C. 大爆炸全量替换** | 一次性换 L0–L2 | **不推荐**：迁移/并行/监管风险最高 |

**推荐 B，但目标明确：自研重写、最终不续订 Avaloq；不是永久双核。**

时间：

- **0–6 月**：业务 case/数据基线/供应商 RFI；
- **6–18 月**：自研家族核心 + 自研 L0 模块（Avaloq 仅参考/迁移）；
- **18–36 月**：新 L0 按产品/辖区迁移；
- **36–48 月**：Avaloq 不续订/退出；自研平台单核运行。

---

### 6. 迁移策略

1. **Strangler**：按旅程/产品/辖区逐步替换，不一次性切。
2. **Data ownership**：自研新核心为家族/授权/证据/账本事实源；Avaloq 仅迁移参考。
3. **Reconciliation**：双跑/对账/差异解释；每日/每月。
4. **De-customization**：把 `HS$` 定制逐条映射到新配置/API/合作；不复制 544 表。
5. **Parallel run**：关键产品/辖区先双跑；监管/客户同意。
6. **Exit**：合同/数据/归档/供应商过渡；提前谈。

### 8. 给董事会/业务的话

> “Avaloq 是一套优秀的交易/账本系统，但它的主键是账户和交易；我们下一阶段的增长主键是家族、代际、跨境、治理和证据。继续在 Avaloq 上叠加，会把新能力做成影子核心，升级更贵、上线更慢、客户体验更碎。  
> 我们建议分阶段自研替换：先建家族核心；以 Avaloq 为参考和数据迁移来源；再用 18–36 个月把交易/账本重写为自有平台，最终不续订 Avaloq。  
> 这不是 IT 换系统，是 **把客户生命周期变成可复用、可扩展、可衡量的平台**；收入、成本、风险、速度四本账都要算。”

**不要说：**

- “Avaloq 很烂” → 不准确，也不专业；
- “换系统就能增长” → 没有因果；
- “IT 说必须换” → 业务不买账；
- “先换了再说” → 没有迁移/退出计划。
