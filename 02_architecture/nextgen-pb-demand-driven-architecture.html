这份文档回答三个问题，而不是一个。
其一，客户到底为什么痛？——从 21 个案例（20 组公开 + 1 组匿名）的原话与失败场景出发，归纳成 8 个 Job。
其二，客户愿意为哪一个痛付钱？——区分“客户付费”“客户通过信贷/交易付费”“银行自己付费”“纯基础设施”。需求强度不等于付费意愿。
其三，系统应该长什么样？——18 个模块、7 层架构、4 个付费层级。
不做什么：不重复厂商的功能清单；不复述 21 个案例；不做没有依据的市场规模测算。§6 不是功能对照表，而是对 incumbent（Avaloq）的平替判定。评分是序数（1–5），用于排序，不用于报价。

§0 读法：为什么从痛点开始，而不是从竞品开始

0.1 旧版是 competitor-first，这一版是 demand-first

旧版《独有能力判定》先问：Avaloq 有什么、Aladdin 有什么、HSBC 能建什么。它回答的是“能不能赢”。这一版先问：21 个案例里的客户在什么时刻愿意付钱、为什么换银行、为什么留存。它回答的是“值不值得建、谁来付”。

两个问题都重要，但顺序不能反。先看竞品，容易得到一个“功能对照表”；先看痛点，才能得到一个“价值链条”。功能对照表告诉你哪里可以差异化；价值链条告诉你差异化能不能收钱。

0.2 三个判断

判断含义对架构的直接后果
客户不买模块，客户买结果客户不会为“客户主数据”“IBOR”“工作流”付钱；他们为流动性、确定性、连续性、被理解付钱。模块必须挂在“Job”上，而不是挂在“功能清单”上。
需求强度 ≠ 付费意愿最痛的往往是合规、证据、数据一致性——这些是银行必须承担的 COGS；最愿意付钱的往往是带交易、带对手方、带截止日的时刻。架构必须区分“收入模块”与“成本模块”，并用收入模块养成本模块。
核心系统的价值是可交付性不是功能数量，而是让高付费意愿的服务能被交付、被证明、被规模化。“证据与 as-of”不是附属功能，是所有高价值模块的地基。

0.3 评分方法：N / W / Payer

维度定义1–5 分怎么打
N（Need）客户需求强度：覆盖多少人物、发生多频繁、失败代价多大、是否阻塞其他需求5 = 多组人物、频繁、失败代价极高、阻塞其他需求；1 = 少数人物、偶发、可替代
W（Willingness to pay）客户/银行愿意为它付钱的程度5 = 客户愿为它付溢价或按信贷利差付费；4 = 客户愿打包付费/显著提升留存；3 = 客户视为应有服务；2 = 银行付钱降本；1 = 纯基础设施
Payer谁付钱客户（顾问费/家族办公室费/信托费）、客户（信贷利差/安排费）、客户（FX/产品利差）、银行（成本/风险）、共享

证据来源：21 个案例的“场景 · 推演”与“六问”；旧版能力判定；Avaloq / Aladdin / Addepar 公开能力。评分为序数判断，不是市场调研；正式立项前须用 10–15 个客户访谈与 5 场 RM 工作坊校准。

0.4 一条主线

21 个案例 → 8 个 Job → 18 个模块 → 4 个付费层级。
这条主线的核心不是“做更多”，而是把客户最愿意付钱的四个时刻（身份变化、授权变化、资金变化、结构变化）变成可交付的服务；其余模块是让这四个时刻能够被交付的地基。

§2 需求强度：25 条痛点、三个断层与痛感重排

2.1 痛的分布不是均匀的

21 个案例里，真正让客户“睡不着”的不是日常配置，而是四类变化时刻：身份变化（移民、IPO、退市、国籍）、授权变化（失能、身故、争议、接班）、资金变化（变现、质押、信贷、税务到期）、结构变化（信托、实体、分家、基金会）。日常配置是低频痛；变化时刻是高频恐惧。下一代核心系统如果只能在“日常”里工作，就会在客户最需要银行的那一天缺席。

#11 集团内信息隔离（Chinese Wall）　J2/J8　N4

场景：郑裕彤家族同时是企行客户、私行客户、信托委托人、上市公司大股东；郭鹤年家族在两个 RM 处各知一半。集团要合并看敞口（信用/集中度/关联交易），但投行部知道的信息不能流到私行，反之亦然；墙的方向（谁不能看谁）、时点（交易前/后）、辖区（墙的法律依据）都不同。
失败链：不合并 → 集团敞口低估 → 授信/集中度失控；合并但不管墙 → 信息滥用 → 监管处罚/声誉。
系统必须回答：这个客户群在集团各实体的合计敞口是多少；哪些信息可以跨实体流动、向哪个方向；这笔指示/授信依据的是哪一版墙规则；谁批准了例外。
落点：横切“信息隔离”规则 + M17 集团敞口 feed + M09 预检硬阻断 + M16 留痕 + M03 可见性。
验收：同一客户群四视角敞口（企行/私行/信托/市场）可合并；任一跨墙访问有目的/依据/审批；隔离违规可阻断并留痕。

#15 遗产认证/冻结与紧急流动性　J6/J5　N4

场景：郑裕彤身故，遗嘱认证（probate）在 HK/UK/开曼同时进行；账户冻结，但家族要付丧葬、医疗欠款、遗产税、员工工资、贷款利息。银行如果只能“等文件”，客户会先失去现金流，再失去信任。Avaloq 的信托产品定义清楚，但 probate 不是一等事件，遗产费用与紧急支付也没有对象。
失败链：死亡 → 账户冻结 → 家庭无现金 → 紧急借款/卖资产 → 税负与折价 → 关系破裂。
系统必须回答：哪些账户被冻结、哪些支付可豁免/可垫付；紧急支付的授权人是谁；每笔支付对应哪份文件/哪条法律；垫付的优先级与追偿路径。
落点：M03 probate 状态、M10 紧急流动性/遗产贷款、M14 遗产税/到期日、M16 法院文件。
验收：probate 案件 T+1 建立；紧急支付清单与授权链可查；遗产税到期日前 30 天预警。

#16 授权文件过期/失效　J2/J6　N4

场景：何氏妻子的 POA 是 10 年前签的，银行登记已过期；郑裕彤的授权在 CEO 辞任后失效，但系统仍显示有效；客户失能后无法补签，家属拿着“看起来有效”的文件来指示。
失败链：文件过期未识别 → 执行无权指示 → 争议/赔偿；或过度谨慎 → 拒绝合法指示 → 客户流失。
系统必须回答：这份授权何时生效、何时失效、覆盖哪些账户/辖区/事项；今天是否仍有效；失效后谁接替；银行是否已登记/验证。
落点：M03 AuthorityDocument 状态机、M16 文件生效链、M12 身份状态、M14 义务到期。
验收：任一授权 T+0 可判定有效/失效；到期前 90/30/7 天预警；失效自动触发“主语切换”流程。

#17 退出税/遗产税/赠与税　J4　N4

场景：Mittal 离境后仍有 10 年英国尾随；客户从英国移居新加坡，触发退出税；把股权赠与子女，触发赠与税/遗产税；同一笔财富在三个辖区被征两次。
失败链：只算所得税 → 漏掉退出税/遗产税 → 客户在交易后才发现 → 追悔/诉讼/流失。
系统必须回答：这次身份/居住地/赠与/继承变化触发哪些税种；纳税时点与估值日；哪些抵扣/协定可用；谁申报；不处理的后果。
落点：M13 TaxEvent/规则包、M14 申报/到期、M12 身份变化触发。注意：EasyTax 只做申报；缴税与建议不在 Avaloq 的 M13 范围内。
验收：身份/赠与/继承事件自动生成税务清单；任一税种可给出“辖区 × 日期 × 依据”；与外部顾问的接口有责任边界。

#25 APP 欺诈/深度伪造　J2/J8　N4

场景：客户接到“RM”的视频电话（deepfake），指示把 500 万美元转到新账户；或授权人的语音被克隆，绕过电话验证；或客户被诈骗后要求银行赔偿。
失败链：身份验证只看声音/视频 → 转账 → 发现被骗 → 追回困难 → 监管/声誉/赔偿。
系统必须回答：这笔指示的身份/意图如何验证；设备/行为/关系是否异常；是否触发二次验证/冷静期；谁批准了例外；事后证据链是否完整。

验收：高风险支付强制多因子/回拨验证；deepfake 风险评分可解释；欺诈案件 24 小时内可还原全链。

2.7 需求强度的反直觉结论

最深的需求，往往不是最愿意付钱的需求。授权、合规、证据、数据一致性是“没有它会出事”的需求，客户默认银行应该做好；Pre-IPO 流动性、家族治理、税务协调是“有它更好”的需求，客户愿意为此付溢价或承担信贷成本。架构必须同时服务这两种需求，但商业模型必须区分它们。
本轮新增的判断：“不可逆”比“高频”更该优先。失能/身故、文件生效链、probate、POA 过期、deepfake 都是低频但不可逆；它们不产生收入，却决定客户是否在最重要的那天留下。

2.8 来自 Avaloq 一线的四条修正：哪些是“没有”，哪些是“有但不联动”

本节把 Avaloq 同事的反馈单独列出，因为它修正了本文此前的两个判断：Avaloq 并不是“没有账户/授权/受益人/决策人”，也不是“完全不碰税”。真正的差距在事件当天的联动、四层税务边界、生态合作的对象化，以及私人股权自动化的“人审边界”。

#一线反馈它修正了什么系统含义落点
1Avaloq CRM 对投资账户有账户/授权/受益人/决策人四类记录；信托产品定义清楚。此前写成“家族/信托/授权只有字段”，过重。准确说法是：四类记录存在，但它们是账户级、静态的；失能/身故当天不自动联动，跨境 probate 不在模型里。不是“补字段”，是“补事件 + 生效日 + T+0 快照 + 跨境程序”。M03/M16/M14；对象：IncapacityEvent/DeathEvent、EstateExpense、EmergencyPayment、PrimaryClientSwitch。
2Avaloq 能算税、能生成申报，也有扣税/缴税能力（同事口径）；EasyTax 只报税；HSBC 的 Avaloq 主要对上报身份做 CRS/FATCA 尽职调查，不做主动税务服务。此前把“税务计算”与“税务服务”混在一起。准确说法是四层：计算 ≠ 申报 ≠ 缴税 ≠ 建议。EasyTax 只覆盖申报；Avaloq 本身覆盖扣缴/缴税（需区分源头扣缴与个人申报缴纳）；建议由外部顾问完成，银行不做。M13 做“可复算的计算 + 申报包 + 扣缴/缴纳接口 + 协调”，不输出建议；银行与外部顾问之间要有责任边界与证据包。M13/M14/M16/X4；对象：TaxPayment、FilingPackage、PartnerReferral、EvidencePack。
3RM 会私下推荐避税模式、会计师、律师、家办；具体服务与 HSBC 无关。这是“生态合作”的真实起点，也是最大合规风险：非正式推荐 = 无记录、无同意、无责任边界。不能把它洗成“银行建议”，也不能继续留在邮件/微信里。把推荐变成对象：合作方注册、转介案件、客户同意、费用披露、责任边界、证据包；数据复用只做去标识化/聚合，不做客户 A 的原始信息转卖给 B。M15/M16/M17/M18/X4；对象：PartnerRegistry、ReferralCase、DataSharingConsent、NextBestAction、EvidencePack。
4Pre-IPO/私人股权目前大量手工：估值、质押、卖方贷款、或有对价、非现金股权；风险评估是难点。此前只写“要联动”，没写“哪些能自动、哪些必须人审”。准确说法是：数据采集、估值区间、LTV、税务计算、追保监控可自动化；估值判断、质押审批、谈判、退出执行仍由人。自动化到“可计算、可监控、可举证”为止；风险判断留在估值委员会/信贷委员会/律师。M06/M10/M16；对象：UnlistedValuation、PledgeOfUnlistedShares、VendorLoan、EarnOut、ValuationGovernance；详见 §5.3。
一句话：Avaloq 的缺口不是“完全没有”，而是“有记录、没事件；有计算、没边界；有合作、没对象；有流程、没自动化”。这四句话决定了本轮新增的对象，而不是新增模块。

L1 客户与家庭

L3 产品与流动性

L4 税务、监管与义务

L5 运营与证据
回答“谁来做、做到哪一步、怎么证明”。不产生收入，但决定收入模块能否被监管/客户接受。

回答“事实从哪来、怎么复用、怎么让 RM 更快”。这是规模化与成本-to-serve 的地基。

4.5 生态合作与数据复用：不新增模块，新增四个对象组

税务师事务所、律所、估值师、受托人不是“供应商”，而是交付链上的共同责任人。系统要做的不是把他们的工作搬进来，而是把“谁在什么授权下、为什么目的、提供了什么证据、谁依赖了它”变成可查的对象。数据复用同理：客户 A 的信息可以帮助“同类客户”的服务设计，但不能以原始形态流向客户 B。

层对象必须回答边界 / 控制落点
合作方PartnerRegistry谁（税/法/估值/信托）、哪个辖区、什么牌照、什么能力、有无利益冲突、SLA 是什么只注册经法务/采购/合规准入的机构；禁止“RM 私人推荐”进入生产M15/M16/X4

证据EvidencePack合作方给了哪份文件/哪个版本/哪个 as-of、谁依赖了它、银行据此做了什么证据可追溯、可撤回；合作方结论不等于银行结论M16/M17

L1 同一客户·跨实体在客户本人授权范围内，合并企行/私行/信托/保险视图超出同意范围共享；把投行信息流入私行目的限制、Chinese Wall、可见性分级

§6 与 Avaloq / Aladdin / Addepar / UBS 的边界：平替对象与能力标尺

这个项目的起点不是“在 Avaloq 上加一层界面”，而是平替 Avaloq。所以本节不做功能清单对照，而回答三个问题：Avaloq 在 8 个 Job 上结构性缺什么；什么算“已经平替”；Aladdin / Addepar 在这条路径上是组件还是替代品。

Avaloq 是成熟的核心银行与财富平台：账务、结算、监管报表、税表工程化，都是应当继承而不是重写的资产。§2.9 的一线反馈修正了“它什么都没有”的写法：结算/多登记、文档版本、集团墙、税务扣缴、ACL、联系方式是强项；下表把强项与真正的语义缺口分开。在 21 个案例提出的 8 个 Job 上，它的数据模型仍决定了几件事不是“还没做”，而是在现有语义层上做不出来。

6.2 平替的判定标准：关掉 Avaloq 之后，8 个 Job 还能不能交付

“平替”不是功能对比表的胜负，而是一条可验收的线：下线的是账户主键与账务前端；Avaloq 的结算/文档/墙/扣税/ACL 可作为继承或并行服务，不要求一次性重写。五条前置条件：

  • 主键换掉：账户不再是主键，人—家庭—实体—资产—权利—义务是；账户只是资产的一种载体。
  • 结论可重放：任一历史时点的“谁有权、欠什么、依据哪份文件”都能还原（as-of）。
  • 税务是引擎 + 规则包：全球引擎一次建成，新增辖区是追加规则包、不发版；CN/HK 是首批包，不是范围边界。
  • 迁移可退出：按账户、授权、权利、义务四类迁移，逐类对账，双跑期有明确退出条件。
  • 强项继承：结算/多登记、文档版本、集团墙、税务扣缴、entitlement/ACL、联系方式不重写；Avaloq 继续作为这些能力的源/并行服务，直到替代品通过验收。

§8 结论：一句话的架构

HSBC 下一代 Private Bank Core System 不是“更好的账户系统”，而是一个“家族操作系统”：它知道你是谁、你有什么、谁有权决定、下一步必须做什么、以及怎么证明。
三个引擎：流动性（M06/M10）、连续性（M02/M03/M05）、合规性（M12/M13/M14/M16）。
三种付费：客户为结果付费（顾问/信贷/税务协调）、客户为留存付费（家庭视图/授权/证据）、银行为成本与风险付费（数据/工作流/AI）。

对“每一个模块有多么被客户需要、客户有多么愿意付钱”的最终回答：最需要的是授权、合规、证据、数据一致性；最愿意付钱的是流动性、家族治理、税务协调、私人股权。两者不是同一张清单。架构的价值，是把“最愿意付钱”的六个模块，建立在“最需要但不能收费”的十二个模块之上。

两条新边界（v1.4）：税务做“计算 + 申报包 + 扣缴/缴纳接口 + 协调 + 证据”，不做建议；生态合作只做“转介 + 证据 + 去标识化模式”，不做原始数据倒卖。Pre-IPO 自动化只到“可计算、可监控、可举证”，估值判断、授信审批、谈判与法律意见仍由人。

对 Avaloq 的最终判断（v1.5）：Avaloq 不是纸老虎。它在结算/多登记、文档版本、集团墙、税务扣缴、entitlement/ACL、联系方式上是强项，应该继承；真正的差距是六个语义对象：EconomicInterest、EventSnapshot、ValuationGovernance、ServiceHistory/Handover、Partner/Evidence/Consent、ChannelIdentity。平替的是账户主键与语义层，不是重写它的强项。
