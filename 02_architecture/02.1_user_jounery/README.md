# 02.1 用户旅程（User Journey）

> 目的：把 `02_architecture` 的 25 条痛点，变成 **7 条可用于领导 Demo 的端到端旅程**。
> 每条旅程按同一条链展开：**痛点 → 新客户体验 → 系统体验 → 功能需求 → Avaloq 改造/重写 / Aladdin 复用 / 新增**。
> 本轮**不修改** `03_webpage_design`；这里只产出“故事源文件”，后续再由 03 做成网页。

> 目录名按指定保留为 `02.1_user_jounery`（原文拼写）；如需统一为 `02.1_user_journey`，可在后续一次性重命名。

---

## 1. 先回答：按类别，还是按痛点？

**建议：都不是。按“决策时刻 × 一个主角”建 7 条旅程。**

| 方案 | 问题 |
|---|---|
| **每个痛点一条故事（25 条）** | 碎片化、重复、没有叙事；领导记不住 25 个故事；每条都要重复人物/背景；Demo 会退化成功能清单。 |
| **每个类别一条故事（9 条）** | 抽象化、失去人物与时刻；“税务类”讲不出一个客户为什么在某个星期二需要银行；跨类问题（失能同时是身份/法律/家族/数据）会被切开。 |
| **每条“决策时刻”一条故事（7 条）** | 一个主角、一个触发事件、一条时间线、一次系统揭示；每条自然跨越 2–4 个类别；痛点是“场景节点”，类别是“覆盖标签”。 |

**一句话：痛点用来证明“真的痛”，类别用来证明“覆盖全”，旅程用来让领导“记住并相信”。**

- 25 条痛点全部覆盖（见 `08-capability-map.md`）。
- 9 个类别全部覆盖（身份与授权、税务、交易与登记、法律与文件、家族与传承、流动性与资本、风控与合规、服务与运营、数据与证据）。
- 每条旅程 3–6 条痛点；不追求平均，追求“一个时刻讲透”。

## 3. 每条旅程的固定结构

1. **为什么是这个 journey**：覆盖的痛点编号、类别、Job。
2. **主角与触发事件**：真实公开事实 vs 设计假设分开写。
3. **今天会发生什么**：T0–T+90 的失败链；今天用哪些系统/人/Excel。
4. **新客户体验**：客户看到什么、能做什么、不用再做什么。
5. **系统体验**：RM/系统看到什么；哪些对象、状态、证据在流动。
6. **功能需求**：对象、模块、关键规则、验收。
7. **Avaloq 改造/重写 vs 复用 vs 新增**：四选一（继承 / 扩展 / 新建 / 合作），逐项写。
8. **Aladdin / Addepar / 合作方复用**：哪些不建，直接接。
9. **Demo 分镜（5–7 屏）**：给后续 03_webpage_design 的页面脚本。
10. **验收指标与边界**：怎么证明有效；哪些是假设、哪些不能对外说。

---

## 4. 给领导讲的时候，只讲三件事

1. **一个时刻**：客户在某个星期二遇到什么（D1/D2/D3 任选一个开场）。
2. **一次对比**：今天会发生什么 vs 明天会发生什么（同一个人、同一天）。
3. **一条链**：客户体验 → 系统体验 → 功能需求 → 继承/扩展/新建/合作。

> 不要按“25 条痛点”逐条讲；痛点只在对应旅程里出现一次，作为“证据节点”。

---

## 5. 与 03_webpage_design 的关系

- 本目录是**故事源文件**：人物、时间线、对话、系统对象、Avaloq 决策、Demo 分镜。
- `03_webpage_design` 是**网页实现**：本轮不动；后续每个“Demo 分镜”对应一个页面区块/交互。
- 现有 03 的 UC1–UC4 是上一代 demo；本目录的 D1–D7 是新架构 v1.5 下的新一代故事，后续可替换/并列，不在此轮决定。

## 6. 使用边界

- 公开人物只引用已公开事实；不主张其为本行客户；不涉及非公开账户、金额、税务或家庭安排。
- AUM、费率、服务模型、时间线均为**设计假设**，用于 Demo，不是客户数据。
- 匿名案例（何氏）不对应任何真实个人；D7 为合成客户。
- 许家印信托案按公开报道写为“香港高院 2025-09-16 任命清盘人为资产接管人（临时接管/保全，并非最终裁定信托无效）”；对外引用前须法务复核。
